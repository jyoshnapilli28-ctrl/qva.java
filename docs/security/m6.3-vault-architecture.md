# M6.3 local vault architecture

Enable the experimental frontend when packaging locally with VITE_QVA_LOCAL_VAULT=1. The default build excludes the navigation item and vault route registration from the React workspace. Spring Boot provides the shell for /app/vault just like other workspace routes. Setup and unlock require the existing authenticated, approved browser device. No endpoint, backend storage, migration, or change to private relay behavior was added.

## Storage format

IndexedDB database qva-local-vault, schema 1, object store devices, indexed by the approved QVA device UUID. The database is isolated by browser profile and origin. Concurrent setup uses an exclusive browser lock and the object store's insert-only add, so another tab cannot overwrite an initialized record.

| Field | Format 1 |
| --- | --- |
| version | Integer 1 |
| deviceId | Approved workspace device UUID that is also the record key |
| kdf and iterations | PBKDF2-SHA-256, exactly 600000 |
| salt | 16 random bytes |
| cipher and nonce | AES-256-GCM with 12 random bytes |
| key | ECDSA-P256, for the local-only sample signing key |
| ciphertext | Raw AES-GCM output including trailing 128-bit authentication tag |

Associated data is the UTF-8 encoding of a fixed-order JSON array with domain string “QVA local device vault”, format version, device ID, KDF name, iteration count, salt byte array, cipher name, nonce byte array and key algorithm. Validation rejects other algorithms, versions, iterations, field counts, device bindings, or unbounded byte lengths before derivation. The authenticated binary plaintext starts with payload version byte 1, then a PKCS#8 length byte, the P-256 PKCS#8 private key and its 91-byte SPKI public key. A future MLS state format requires a separate explicit migration.

## Lifecycle

The password starts in uncontrolled form fields. Inputs have no submission names. Submission resets the form and transfers UTF-8 bytes to a dedicated module Worker. The Worker derives an unextractable AES key, generates a local-only P-256 signing key, and stores only authenticated ciphertext and its header. Successful unlock decrypts the record, imports a non-extractable private CryptoKey, and returns status only. The Worker exposes no signing API yet.

One Web Lock per vault/device keeps setup/unlock and retained private keys exclusive across cooperating tabs. Explicit lock, leaving the vault route, detected session expiry or lost device approval, page departure, and logout discard the worker. Logout and detected expiry broadcast to cooperating tabs. Successful refresh or browser restart returns to the locked state. Eligibility and session expiry leverage the existing workspace poll and live reconciliation. The inactivity policy is five minutes by default, configured at build time with VITE_QVA_VAULT_IDLE_MS from 1000 to 900000. Browser scheduling can delay a hidden tab timer. Upon visibility change or the next activity an expired deadline is checked again.

Malformed, unsupported, or missing expected records enter recovery-required state without overwriting the stored record. Wrong-password and authenticated-decryption failure share an error. Browser/site data clearing, origins and private contexts can affect durability. There is no backup, synchronization, escrow, or cross-device key transfer.
